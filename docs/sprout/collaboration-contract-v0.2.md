## 0. 如何使用这份约定

- **已确认约束**：本线已有明确产品决定或安全底线，不能由另一份草稿静默覆盖。

## 2. 产品范围与工程拆分【已确认约束＋待映射】

### 2.1 产品目标

容器作为DSH唯一运行底座，建设可组合、可定制、可扩展的Android工作台。停止投入的是Android原生DSH运行时，不是Android壳、桥、终端、Root／Shizuku／ADB、实体／虚拟屏或独立应急。

高刷、Gecko一体包、Root模块支持是本线确定需求；桌宠当前只排单，不做HTML／原型。后续顺序调整需明确批准，不因本协议自动提前实现。

### 2.2 三种数量不能相减

- 我方18项是逻辑职责草案，不要求18个Gradle工程或18个APK。
- 对方21项可作为状态所有权／失败域地图，重点吸收配置、凭据、诊断、进程退出证据、受管安装、legacy和应急的明确归属。
- 编译模块数量由依赖、资源合并、测试发现和构建约束决定，不先凑9、18或21个空工程。

建议双方维护一张总表：

| 逻辑职责ID | 唯一状态owner | 持有资源 | 对外接口／事件 | 编译落点 | 回归归属 | 故障恢复 |
|---|---|---|---|---|---|---|
| 待双方逐项填写 | | | | | | |

### 2.3 内置可组合，不等于动态安装平台

首期只接**随包可信模块**。编译期工厂／接口可以同时支持注册、贡献、启停、撤销与恢复；这些机制不要求第三方动态代码加载。

暂不做任意Dex／JS／脚本加载、完整模块市场、不可信原生扩展。以后外部分发另评信任、签名、兼容、隔离与撤回。

## 3. 依赖方向与唯一权威状态【建议共同采用】

依赖方向：业务模块→稳定API；适配器→API及已有实现；宿主组合根装配实现。稳定API不依赖具体Activity、Fragment、全局Context、容器内部对象或raw shell。

以下状态必须有明确唯一owner，消费者仅取快照或提交请求，不复制第二套权威状态：

| 状态域 | 必须明确的权威与职责 |
|---|---|
| Web生命周期 | 实例、代次、停止意图、鉴权与复用 |
| 环境与受管安装 | runtimeId、输入证明、候选／试运行／提交／恢复 |
| 维护与租约 | 维护屏障、运行租约、取消及准入 |
| 进程身份与退出证据 | PID出生身份、双次核验、guest／launcher退出次序与信号结果 |
| 授权与派发 | 系统授权、本地能力策略、任务许可、撤销epoch、一次性派发 |
| 虚拟屏 | Core owner、连接／显示代次与观察／输入身份 |
| 数据事务 | 配置、备份／恢复、迁移、写入提交与未知原件保护 |
| 插件 | writer锁、启停意图、pending事务与热检查 |
| 终端与更新 | 独立终端会话；更新候选／下载／安装请求，各有明确owner |

“进程身份与退出证据”及“受管运行时安装”需要显式接口与测试归属，即使首期不单拆Gradle工程。UI不以缓存或页面生命周期代替业务状态；切页不是任务结束。

## 4. 最小内置模块契约【待对齐提案】

首期只实现首个闭环需要的字段和接口，不冻结全部未来API。

| 契约 | 最小内容 |
|---|---|
| 身份 | 稳定moduleId、版本、hostApiRange、受信entryId |
| 依赖 | 缺失、环、版本不兼容的拒绝语义 |
| 贡献 | 稳定contributionId、slot／route、标题／图标引用、可见性 |
| 能力声明 | domain／action／resourceScope／purpose；声明不等于授权 |
| 配置 | 命名空间、schemaVersion、校验、原子提交、迁移与last-known-good |
| 生命周期 | 注册／启用／停用／销毁、失败原因与幂等资源句柄 |

规则：

1. entryId映射宿主随包工厂，不接受任意类名、命令或文件路径。
2. 重复ID不得覆盖已有贡献；不允许半注册成功后留下不可见残留。
3. 模块启停与页面mount／unmount分开。
4. 停用先退休代次／拒绝新调用，再取消自有作业、订阅与旧回调，然后撤贡献／窗口及资源，最后回报清理结果。
5. 停用不删除用户配置，不结束无关DSH会话，不移除必需安全恢复或法定许可入口。
6. 进程恢复只重建注册与呈现，不自动重放Root写入、删除、网络写入或屏幕动作。
7. 故障隔离先如实指可控异常／停用／安全模式；同进程崩溃并不保证宿主存活。

首例：**关于／许可卡片→既有页面**，不新增敏感能力；验证声明、注册、卡片、导航、排序／隐藏、重启恢复和停用清理。关于页中的显式外部链接由宿主处理，不能把整页称作绝无外部动作。

## 5. 能力分域与许可【建议共同采用】

授权上限取交集：

> 原生可验证caller上限 ∩ 当前任务许可 ∩ 操作／资源范围 ∩ 系统授权 ∩ 当前代次／有效期。

后端可用≠业务获准；global allow不能越过显式拒绝或扩大caller上限。Root管理与普通模块、DSH调用分域，不能依赖提示词或全局non-strict达成“DSH默认只读”。

能力请求建议字段：

- operationId、协议版本、操作类型；
- 原生确定的caller及模块启用代次；
- 必要的runtime／session／turn身份；
- 目标对象／FD／路径范围及摘要；
- policyRevision、authorityEpoch、单调时钟截止；
- 对有副作用派发的一次nonce／permit，以及授权依据。

执行侧派发前重验目标、授权、撤销与截止；排队消耗TTL。若使用MAC，要明确规范化序列化、所有覆盖字段、密钥归属、轮换／重启失效及一次消费语义。

**信任限定：**共享bearer token不证明module身份；自报caller不可信。同进程HMAC可校验无钥输入篡改，不是对任意同进程恶意代码的沙箱。独立进程提供故障隔离价值，但不自动等于独立UID／权限隔离。

## 6. 执行结果：先保语义，再定五态或六态【待双方冻结】

建议把以下轴分开表达，而非强行用单个枚举承载：

1. **派发事实**：未派发／已派发／未知。
2. **执行结论**：拒绝、成功、失败、已证部分完成、未知。
3. **取消事实**：未请求／已请求／已确认停止后续；不抹掉既有副作用。
4. **效果验证**：已验证／未验证／不适用，说明验证范围。

参考映射（不是已冻结wire schema）：

| 场景 | 可映射的摘要结果 | 必须保留的信息 |
|---|---|---|
| 派发前策略拒绝 | REJECTED | dispatched=false、原因 |
| 派发前取消／过期 | NOT_SENT | dispatched=false、取消／过期原因 |
| 已证实全部完成 | COMPLETED | 完成范围；不能默认为界面效果也已验证 |
| 已证实只完成一部分 | PARTIAL | 已完成与未完成范围；不能仅因没验证效果就叫部分完成 |
| 派发后失联或结果不明 | UNKNOWN | 副作用可能发生，不声称已退出或未发送 |
| 已派发且明确失败 | 需定义FAILED或结构化outcome字段 | 失败阶段、有无既有副作用；不能误映射为NOT_SENT |
| 已请求取消但可能已执行 | 依证据为PARTIAL／UNKNOWN／其他已证结果 | cancelRequested与执行事实独立 |

未知tag应fail-closed，不解释成成功。UNKNOWN不自动重放；**新观察／新凭据只是重新判断的前提，不自动授权重做不可逆副作用**。

## 7. 存储、网络、Root与屏幕不变量【建议共同采用】

- 私有文件、逐文件picker、SAF树、广泛共享根分别授权；主动picker不以MANAGE作为前置，选中一个文件不授予整根存储。
- 文件写入先验证对象再截断；SCAN_LIMIT不当NOT_FOUND；创建后超时不盲重试或盲删不明归属文件。Provider不可强抢占，协作deadline不等于墙钟硬退出。
- 网络区分入站桥、LAN代理、出站请求／传输；每跳重定向重验目标，跨源不转凭据。模块不获得代办密钥；broker不是系统防火墙。
- Root管理先识别／握手／清单，只开放验证过的管理器与功能；写生命周期另卡，旧Root写入口封闭／降权前不开。不自动执行第三方模块脚本。
- 实体屏与虚拟屏不混用实例／代次／观察／输入凭据；暂停、接管、撤销后拒绝新动作，未知不重放。密码写入拒绝在原生执行点，不靠快照掩码代替。
- 进程停止只针对已核身份，不按端口、名称、进程组或裸PID；结果不明保留现场。
- 独立应急运行根不能依赖正常容器迁移或普通模块可用；受控修复仍需授权，不因“应急”绕策略。

## 8. 自更新与覆盖升级的准确边界【已确认约束】

“嫩芽候选暂不接入正式更新通道”的定义：

- 仅Rebirth候选禁用正式feed的启动／手动检查、下载、安装取包和旧更新任务恢复，并给出手动更新说明。
- 正式包不启用候选开关，原更新链与包名／证书校验保留。
- 没有停用正式更新服务器，没有删除系统安装器覆盖升级能力，没有取消受管维护、试运行或数据恢复门禁。
- 后续同Rebirth包名、同候选签名、合适versionCode的包仍可经用户手动安装升级；尚未真机演练，不宣称已通过。
- 候选未来是否建设独立更新通道另定。对方只停“自动段”的方案可适用于其发行线，不自动覆盖本候选隔离策略。

APK回退≠数据回退；tag不是Android允许降级的证明。无安全降级路径时评估更高versionCode的前向修复，不用卸载清数据解决兼容。

## 9. Kotlin／Rust工程约定【建议＋待评审】

### Kotlin

- 增量新核心／模块边界优先，不全库翻译，不默认Compose；保留现有Fragment／View及视觉门禁。
- 先理依赖、状态owner、测试发现与生成脚本路径，再拆编译工程。
- Java／Kotlin公开边界明确空值、不可变DTO、可取消句柄、错误与生命周期，不暴露内部协程作用域或实现单例。
- Kotlin具体版本、AGP支持方式、格式器／静态检查和离线依赖需同批锁定；按模块迁移还是允许适配边界混写，由技术验证决定，不为语言纯度做无关重写。

### Rust

Rust尚非本线已批准实现范围。可优先评审压缩／摘要／计划校验旁路，前提是有可复核收益、差分测试和JVM回退。

- 不接管进程身份、信号、PTY、设备桥、容器启动器或guest插件事务。
- 纯计算优先采用明确类型化函数；若暴露PlanEnvelope／execute，必须列封闭kind、目标／FD、允许副作用与许可范围，不能因无裸字符串就声称无危险执行。
- catch_unwind仅覆盖可展开的Rust panic；abort、原生崩溃、JNI异常、缓冲区与对象生命周期另定。
- 锁定Rust／NDK／依赖、16KiB兼容、许可证与构建来源；区分.so字节复现和压缩结果内容等价，不混用验收。
- 独立进程／独立UID／IPC／网络隔离若需要，单独做威胁模型，不塞进“Rust内核”一句话。

## 10. 交付、测试与协作【建议共同采用】

### 每批任务开工前

明确owner、完整SHA／工作树、允许文件、依赖、批准范围、可判定AC、负正控、所需门禁、回退和审查者。一任务一工作树／分支；并行写入分离文件范围。

### 每批交付最小材料

1. 来源／新提交完整SHA、限定diff、输入锁与工具链。
2. API／schema版本和变更说明；状态owner及失败语义。
3. 负控→修复→正控→相关回归，实际命令、退出码、fresh报告。
4. 完整diff独立审查意见与逐项处置。
5. APK若有：实际包名／显示名／版本／ABI／debuggable／证书、输入与资产证明、完整SHA256。
6. 真机／覆盖升级若有：同一APK、设备／系统／WebView、步骤与脱敏证据；未跑明确写未验证。
7. 残余风险、兼容／恢复限制及接入方式；不能用口头“编过了”替代。

源码存在、单测通过、包检查、真机通过分层记录。环境失败、超时、跳过、UNKNOWN不计通过；不设永久失败白名单。测试发现不能因Gradle拆分静默漏类，模块化后应核实际测试归属与计数变化，而非永远固定历史数量。

同一共享手机环境Gradle单实例串行；host脚本可能内部起Gradle，也必须纳入调度。独立CI的并行策略需单独确认资源与依赖，不能与本地规则混为一谈。

敏感权限、提交、推送、合并、构建触发、安装、正式签名和发布分别记录授权；某一仓库可写不等于可随意改另一仓库。

## 11. 对协作草稿需补严的实施条款【待双方评审冻结】

以下逐项回应Kotlin／Rust方向、21状态／9编译模块及A1–A8路线中的待澄清点。不是否定已有工作，也不是要求先造完整框架；目的是把“原则正确”补成可执行、可判失败的契约。原草稿的数量、循环数、热点结论等静态统计，仍需由对应精确源码与测量材料支撑。

### S01 Rust范围：计算接口与执行接口分开

**需补：**“仅旁路计算”与`execute(PlanEnvelope)`携带`argv/mode`容易产生不同理解。

建议首期采用封闭的类型化操作，例如归档压缩、流式摘要、计划验证；逐项写明输入、输出、FD／缓冲区所有权、可写对象、资源上限及取消点。这里的名称只是职责示例，不是已定ABI。

- 计划验证只返回校验结论，不因验证通过而启动任何进程。
- 若确实需要产生副作用的execute，另列允许kind、执行器、目标范围与授权来源；不得以“无裸字符串”替代完整能力控制。
- argv是已解析的参数数组，不隐式转交shell解释；纯计算API不因存在PlanEnvelope就自动拥有设备执行权。

**验收／负控：**未知kind、额外字段、非法类型／长度、任意shell入口、验证器尝试派发命令均拒绝；纯计算测试应能证明没有进入设备／进程执行器。

### S02 PlanEnvelope与MAC：字段、绑定和序列化完整

**需补：**草稿列出的字段不含target，但另一段又把target纳入MAC；caller、nonce、撤销与时间域也需一致。

至少明确：

| 字段域 | 要回答的问题 |
|---|---|
| 协议／操作 | schemaVersion、封闭kind、operationId；是否允许未知字段 |
| 调用身份 | caller由谁认证，module／runtime／session等绑定哪些，不能由请求者自报后直接信任 |
| 目标 | 对象／FD／URI／进程出生身份／路径范围，如何固定目标而非只签一个易变化的字符串 |
| 参数 | argv／mode及其他执行相关字段，谁解析、如何防规范化歧义 |
| 策略与撤销 | policyRevision、authorityEpoch、启用代次，派发前如何重验 |
| 时间 | 单调时钟截止、排队消耗、时钟所属进程／实例，重启后旧票如何失效 |
| 一次消费 | 对副作用许可的nonce／permitId、claim原子性、并发重复请求如何裁决 |
| MAC | 规范化编码、域分隔、算法／版本、覆盖的全部执行字段、密钥生成／持有／轮换 |

同一字节序列应有唯一解释；明确UTF-8、字段顺序或确定性编码、重复字段、缺省值、整数范围、长度与路径规范化，不能先签后再改变解析语义。

**验收／负控：**逐字段篡改、目标替换、伪caller、异域／旧代票、过期／排队过期、撤销竞态、重复claim、重启旧票、重复字段和不同规范化写法均有明确结果。纯计算若无副作用，不必机械套一次性派发nonce；由其威胁模型说明。

### S03 安全承诺：分清HMAC、进程与UID边界

**需补：**“不可伪许可证”“独立进程才是引擎隔离”必须注明保护对象与攻击假设。

- HMAC保护无钥方不能任意篡改已签计划；同进程任意恶意代码若能访问密钥或执行入口，不受此承诺保护。
- 独立进程可提供部分崩溃隔离，通常不自动改变Android UID、文件访问和系统权限。
- 若需要不可信扩展隔离，另列独立UID／isolated process的具体限制、Binder／IPC鉴权、文件与网络边界、密钥分发及系统能力代理；不能一律写“进程化即安全”。

**验收：**威胁模型表明确可信随包、容器调用、不可信外部代码各受何约束，以及已知旁路。未闭合旧万能入口前，不声称全链强制最小权限。

### S04 FFI故障与资源生命周期

**需补：**每入口`catch_unwind`不等于原生故障不会结束App。

需定义JNI线程与attach／detach、句柄／引用生命周期、输入长度、缓冲区分配与释放责任、FD转移、重复关闭、取消与回调线程，以及错误跨边界的表示。

- `catch_unwind`仅捕获可展开Rust panic；abort、内存破坏、段错误、UB等不在其保证内。
- Rust panic不能越过不允许unwind的FFI边界；JVM pending exception也不能被无视后继续调用JNI。
- 句柄应带owner／generation和关闭状态；旧回调、重复释放、跨线程错误使用需可检测。
- 取消只停止后续可取消步骤，不保证已进入系统／Provider调用可强制抢占。

**验收／负控：**可捕获panic、无效句柄、边界长度、内存／I/O失败、取消前后、重复close、旧回调与JVM异常路径有结果；不能在正式用户数据上做原生崩溃故障注入。

### S05 Rust收益、回退与可复现性分别验收

**需补：**现有“唯一热点是deflate”和1.10MiB预算等应关联可复核基线，而不是直接作为既成测值。

先锁代表性小／大归档、文本／不可压缩内容、条目数量、设备／温度／存储／编译配置，比较JVM与Rust：耗时p50／p95、峰值内存、功耗／温升、取消延迟、APK／ABI增量与失败恢复。正式对照前冻结阈值，不看结果后改预算。

分开三种证明：

1. **功能等价**：解压后的成员路径、类型、权限／元数据规则、内容摘要和清单一致，拒绝边界一致。
2. **压缩字节一致**：只有产品确有此要求时才要求；gzip时间戳、排序与实现差异可能导致内容相同但归档字节不同。
3. **本地库构建复现**：锁Rust／NDK／linker／依赖／源码／flags、生成路径与构建信息，比较.so的确定性输出；不是仅有Cargo.lock就自动复现。

`cargo vendor`、许可证／来源、供应链校验与16KiB兼容同时验证。回退在派发前选择实现；若Rust已部分写入，不能再自动调用JVM重做副作用，应先核结果或在受控临时目标事务化后提交。

**出口：**有收益才扩展，无收益或兼容不合格可继续JVM；不能把引入Rust本身算作性能完成。

### S06 五态／六态：取消、部分完成与效果验证不混写

第6节映射须补成字段表及转换表。特别明确：

- COMPLETED指函数返回、系统接受、进程退出还是业务目标完成？不同层必须注明。
- 已执行但明确失败如何表达？没有FAILED枚举时，结构化outcome／error必须保留，不能并入NOT_SENT。
- PARTIAL仅用于有证据的部分完成；“接受动作但效果未验证”应由effectVerified表达，不能凭空声称部分成功。
- 取消前零派发、派发后取消、取消后结果已知／未知分别测试。
- UNKNOWN与PARTIAL都不是自动重试许可；未知tag不能携带“已退出／未执行”断言。

**验收：**双方同输入差分表覆盖拒绝、未派发取消、成功、明确失败、部分写入、回执丢失、未知tag与界面未验证；映射不得丢失副作用事实。

### S07 数据、覆盖升级和候选隔离

**需补：**“双读单写”“dataWrite不变”“每轮可回退”必须写明可兼容范围。

- 分别列正式、Mod、Rebirth的来源包／证书／versionCode与目标包，不把跨包安装当原位升级。
- 列备份、会话、配置、journal、插件事务等schema读／写能力；旁路新字段若会被旧版破坏或忽略，说明恢复行为。
- dataWrite标记不变不证明未改变语义；新旧版本实际互读／恢复需测试。
- Keystore不能解密时保留原密文和原因，不生成替代密钥冒充恢复；系统授权不从备份自动恢复。
- APK降级可能被Android拒绝；tag／开关不是完整回退。必要时更高versionCode前向修复，另验证数据兼容。
- 停候选正式update client与保留系统覆盖安装／维护分开，沿用第8节定义。

**验收：**旧→新、同代覆盖、更新中断、迁移取消、空间不足、旧会话未确认、恢复旧配置、签名不匹配及无法降级都有明确退出；保留未知原件，不以卸载清数据解决。

### S08 18／21／9与A1–A8时间表补齐

**需补：**提供所有9个编译模块、二期2项的完整名称／职责／依赖图，而不是从几轮表格散列推断。21项中无状态纯组装也可单列，但要说明“状态模块”只是分责口径，不代表每项都有独占状态。

明确三个时点：逻辑包／接口引入、真正Gradle子工程建立、Kotlin语言迁移。解决“先破环再建工程”和“A1已有多个编译落点、A8才工程化”的表述差异。

- A1可先落最小内置契约与关于闭环，不要求先完成全部工程拆分。
- Kotlin按模块还是跨Java适配边界混写，由工具链／ABI／测试证明决定，不把按文件禁混写扩成全局重写要求。
- “不做动态安装”和“内置贡献可停用”分开；A1仍验旧回调／许可兜底／恢复。
- 高刷补明确阶段与实测出口；Gecko沿一体包需求独立设计，不等于恢复low变体。
- P0文档评审完成、基线软件门禁完成、真机完成是不同出口，不能共用一个勾。

**验收：**职责映射无遗漏／冲突，依赖无环，测试和生成器路径可发现；拆工程前后用例清单及实际执行计数可对账，没有静默skip。性能及真机需求不在工程化过程中消失。

### S09 权限与维护表述需与实际执行路径一致

现有方法／探针／测试类存在不等于生产已接线。桥协议版本、描述符／launcherInputs覆盖、provider权限、暂停与授权摘要、进程停止预算等说法，绑定精确提交与调用路径复核。

- 每次runtimeId变化是否必进维护，需说明“已有安装环境＋特定入口／版本”的前提；全新安装、受限入口、未安装环境与故障恢复不能一概而论。
- 没有进入描述符的新安全核心不能故意借漏纳管来满足“零维护”目标；先按真实更新契约决定是否纳管。
- Root只读阶段验收包括管理器未知／版本不支持、系统授权拒绝／撤销、跨域票、旧万能入口与global non-strict不扩权。
- 已知安全缺口另卡优先处理，但静态线索不升级为已证漏洞，也不为架构迁移等待而长期搁置。

**验收：**每项结论能给完整SHA、真实入口与反例；代码／自动测试／构建包／真机分别记证据。旧注释、上游CI、自述“已批准”不替代本线验证。
